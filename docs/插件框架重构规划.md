# 插件框架重构规划：以 AgentPlugin 为主体的分层插件体系

> 状态：规划稿（未实施）
> 背景：当前插件框架以 AgentTool 为唯一主体，"插件"概念寄生在工具之上，无法优雅支撑多工具插件、纯前端插件、插件级配置与插件级管理。
> 关联文档：`docs/插件开发说明.md`（现行体系）
> 涉及模块：`hopaw-contract`、`hopaw-infra`、`hopaw-app`、`hopaw-plugin-repo`、`tools/*`

---

## 1. 现状研究结论

### 1.1 现行加载与注册链路

```
plugins/*.jar
  └─ JarPluginLoader（启动扫描 + 热装入口）
      └─ PluginClassLoader.scanAgentToolClasses()   ← 扫描 JAR 内所有 AgentTool 实现类
          └─ 逐个 newInstance() + autowireBean() + asyncInit()
              └─ DynamicToolRegistry.register(jarFileName, classLoader, List<AgentTool>)
                  └─ PluginEntry（key = JAR 文件名，含 tools 列表 + plugin-assets.json 解析结果）
```

消费侧：

- `AgentToolService.getToolSets()`：内置 Bean（`getBeansOfType(AgentTool.class)`）+ 插件工具，逐个 AgentTool 生成一个 `ToolSetInfo`（扫描类上的 `@Tool` 方法）；
- `AgentService.getToolSetFromAgent()`：按 `Agent.tools`（逗号分隔的**工具集名**）过滤 `ToolSetInfo`，交给 `AgentExecutor`；
- 前端 `tools.html` 平铺展示 `ToolSetInfo` 列表（卸载/导出按钮挂在每个工具集上）；
- 插件仓库 `hopaw-plugin-repo`：`packages/<name>/<version>/` 目录 + 导出清单 `PluginExportInfo`（继承自 `ToolSetInfo`）。

### 1.2 问题一的结论：每个插件是不是只能注册一个 AgentTool？

**技术上不是，事实上一却是。**

- 加载器本身支持多个：`scanAgentToolClasses()` 返回 List，一个 JAR 里有 N 个 AgentTool 类会全部实例化并注册（`JarPluginLoader.loadPlugin` 返回 `tools.size()`）；
- 但**整个管理层都建立在"1 JAR = 1 AgentTool = 1 ToolSet"的假设上**，多工具 JAR 是"半残支持"——能加载运行，管理面全面失真：
  - **插件名取第一个工具**：冲突检测 `detectConflicts()` 用 `entry.getTools().get(0).getName()` 当插件名（`AgentToolService` L370）；
  - **版本取第一个工具**：升级判断 `previousVersion = existing.getTools().get(0).getVersion()`（L513/L573/L590，共 3 处）；
  - **导出只带一个工具集的元数据**：`exportPlugin()` 按 `toolName + toolVersion` 匹配**单个** `ToolSetInfo` 生成清单，同一 JAR 的其余工具集元数据丢失；
  - **扫描报告同样取第一个**：`scanPluginInfo()` 中 `result.pluginName` 只在第一个可实例化类上取值；
  - **UI 层混乱**：`tools.html` 每个 `ToolSetInfo` 都渲染卸载/导出按钮，一个多工具 JAR 会显示多个卸载按钮，且都指向同一个 JAR；
  - **配置只有工具级**：`getConfigItems()/getConfigPrefix()`（`tool.<工具集名>.`）定义在 AgentTool 上，插件级公共配置（如一个"数据库插件"给 3 个工具共用的连接信息）无处安放，只能每个工具重复配。
- 现实佐证：`tools/` 下 13 个插件模块**全部只含一个 AgentTool 类**，"一插件一工具"是约定俗成的天花板，而不是框架能力。

### 1.3 现状的其他结构性问题

| # | 问题 | 代码位置 |
|---|------|----------|
| P1 | **插件身份寄生在工具上**：name/version/author/url/icon/keyword 全部定义在 `AgentTool` 接口，本质是"插件元数据"，但载体是工具 | `AgentTool.java` |
| P2 | **注册表 key 是 JAR 文件名**而非插件标识：改名 JAR 即视为不同插件；两个不同 JAR 可装载同名工具集，`getToolSetFromAgent` 按名过滤会同时命中 | `DynamicToolRegistry` |
| P3 | **前端资产已经是"插件级"，但主体仍是 AgentTool**：`plugin-assets.json` 挂在 `PluginEntry`（JAR 级），与 AgentTool 无关；而 `invoke` 通道（`POST /api/plugins/{toolName}/invoke`）和 WebSocket 指令（`cmd.toolName`）却是工具集级。"插件"实际存在两套口径 | `PluginEntry.loadAssets()` / `PluginInvokeController` |
| P4 | **导出/仓库清单以工具集为主体**：`PluginExportInfo extends ToolSetInfo`，仓库条目、版本、描述、图标全部单工具集口径 | `PluginExportInfo` / `PluginRepoService` |
| P5 | **LLM 管理工具（pluginTool）按工具集名操作**，与"装的是插件"这一事实错位 | `ToolManagerTool` |

### 1.4 现状中已经"插件化"、可直接继承的资产

- `PluginEntry` + `PluginClassLoader`：JAR 级生命周期（classloader 隔离、资源缓存、临时文件清理）已经完备，**无需大改**；
- `plugin-assets.json` + `PluginAsset` + `PluginAssetController` + 前端 `plugin-loader.js`/`plugin-hook.js`：前端组件注入体系是天然插件级的，**可直接平移**；
- `@Tool` 方法扫描（`scanToolSet`）、安全级别、审批链路：工具级机制成熟，**保持不动**；
- `Agent.tools` 绑定粒度是工具集名：智能体消费侧**无需破坏性变更**。

## 2. 目标架构：AgentPlugin 主体模型（问题二）

### 2.1 核心思想

把"插件"从 AgentTool 的一个侧面，提升为**独立的一等公民接口**：

```
AgentPlugin（插件主体，1 JAR = 1 实例）
 ├── 插件元数据：name / version / author / url / description / icon / keyword
 ├── 插件生命周期：asyncInit() / destroy() / onConfigChanged()
 ├── 插件级配置：getConfigItems() + getConfigPrefix() = "plugin.<name>."
 ├── 能力声明：getTools() → 0..N 个 AgentTool
 ├── 前端组件：plugin-assets.json（沿用，jar 级）
 └── 通用调用：invoke(Map)（从 AgentTool 上移到插件级）
```

`AgentTool` **瘦身为纯工具**：

```java
public interface AgentTool {
    String getName();            // 工具集名（保持，前端 hook 过滤、执行分组仍用它）
    String getDescription();
    // @Tool 方法 + @ToolSecurityLevel：不变
    // 工具级可选配置（继承插件配置段的子键）
    default List<ToolConfigItem> getConfigItems() { return List.of(); }
    default void onConfigChanged() { }
    // 移除：getVersion/getAuthor/getUrl/getIcon/getKeyword → 归 AgentPlugin
    // 移除：asyncInit/destroy → 归 AgentPlugin
    // 移除：invoke → 归 AgentPlugin
}
```

### 2.2 关键设计决策

**D1 - 一个插件 0..N 个工具**：`getTools()` 返回空列表合法——纯前端组件插件（只注入 js/css/html）、纯 invoke 服务插件（只暴露 `POST /api/plugins/{pluginId}/invoke`）都是合法形态。加载器不再因"没有 AgentTool"拒绝 JAR（现行 `JarPluginLoader.loadPlugin` 中 `classNames.isEmpty() → return 0` 的逻辑改为：无 AgentPlugin 也无前端资产才拒绝）。

**D2 - 插件标识**：`AgentPlugin.getName()` 即 pluginId，全局唯一，作为注册表主键（替代 JAR 文件名）。JAR 文件名仅作物理定位。加载时检测 pluginId 冲突：同 id 已注册 → 拒绝并报告"插件已安装，请走升级"。

**D3 - 工具命名空间**：`@Tool` 工具名保持全局唯一（沿用现行冲突检测），建议约定 `<pluginId>_<method>` 前缀（现状已如此：`gomoku_startGame`）。`ToolSetInfo` 增加 `pluginId` / `pluginName` 归属字段。

**D4 - Legacy 兼容适配（最重要）**：JAR 内**没有 AgentPlugin 实现但有 AgentTool 实现**时，加载器自动构造一个 `LegacyAgentPluginAdapter`：

```
LegacyAgentPluginAdapter
 ├── name/version/author/icon/keyword/description ← 取第一个 AgentTool 的对应值（与现行行为完全一致）
 ├── tools = 扫描到的全部 AgentTool 实例
 └── invoke → 委托给第一个 AgentTool.invoke（保持 /api/plugins/{toolName}/invoke 兼容）
```

现有 13 个插件**零改动**即可在新体系下运行；后续逐个迁移到显式 AgentPlugin。

**D5 - 接口契约草图**（hopaw-contract 新增）：

```java
public interface AgentPlugin {
    String getId();                          // 插件唯一标识
    String getDescription();
    default String getVersion()  { return "1.0.0"; }
    default String getAuthor()   { return "Agent Plugin"; }
    default String getUrl()      { return "https://gitee.com/hgflydream/hopaw-agent"; }
    default String getIcon()     { return "plugin.svg"; }   // jar 内 static/icons/plugins/
    default String getKeyword()  { return ""; }
    default void asyncInit()     { }
    default void destroy()       { }
    default List<ToolConfigItem> getConfigItems() { return List.of(); }
    default String getConfigPrefix() { return "plugin." + getId() + "."; }
    default void onConfigChanged() { }
    default List<AgentTool> getTools() { return List.of(); }   // 0..N
    default Map<String, Object> invoke(Map<String, Object> params) { ... 默认不支持 ... }
}
```

`AgentTool` 上被移除的元数据方法**暂以 default 实现 + @Deprecated 保留**，返回所属插件（通过加载期注入的 PluginContext）的值，给生态一个迁移窗口期。

## 3. 管理层级拆分（问题三）

### 3.1 两级模型

```
一级：插件管理（PluginRegistry / PluginManagerService）
 ├── 安装 / 升级 / 卸载（以 pluginId + version 为准）
 ├── 启用 / 禁用（新增运行时状态，禁用 = 工具不进 ToolSets、前端资产不注入）
 ├── 插件级配置（plugin.<id>.* 配置页）
 └── 插件元数据展示（版本/作者/来源/前端资产数/工具数）

二级：插件内工具管理（ToolManagementService）
 ├── 工具集（AgentTool）列表 + @Tool 方法明细（参数/描述/安全级别）
 ├── 工具级配置（插件配置段的子段）
 └── 工具集启停（可选：插件内单个工具集的开关，粒度到 AgentTool）
```

服务层拆分（现 `AgentToolService` 职责过载，一并拆解）：

| 现类 | 拆分后 | 职责 |
|------|--------|------|
| `AgentToolService` | `PluginManagerService` | 插件安装/升级/卸载/启停/导出、冲突检测、Legacy 适配 |
| `AgentToolService` | `ToolSetService` | ToolSet 扫描（`scanToolSet` 逻辑平移）、按 agent 组装 `List<ToolSetInfo>`、`getToolNameAndDescriptionMap` |
| `DynamicToolRegistry` | `PluginRegistry` | key 从 jarFileName → pluginId；`PluginEntry` 持有 `AgentPlugin` 实例 + `List<AgentTool>` + assets |

### 3.2 配置两级化

- 插件级：`plugin.<pluginId>.<key>`，`AgentPlugin.getConfigItems()` 声明，`onConfigChanged()` 在插件配置保存后触发；
- 工具级：`plugin.<pluginId>.tool.<toolSetName>.<key>`（或沿用 `tool.<toolSetName>.`，Legacy 插件保持旧前缀以不丢存量配置——**推荐双轨**：Legacy 插件旧前缀不动，新 AgentPlugin 插件用新前缀）；
- `ConfigChangeEvent` 分发：先匹配插件前缀 → 触发插件 `onConfigChanged()`，再逐工具匹配工具前缀 → 触发工具 `onConfigChanged()`；
- 前端配置页：一级页面选插件，二级页内分"插件配置"区块 + 每个工具集的"工具配置"区块。

### 3.3 智能体使用侧：仍以 ToolSet 为主体（不变）

- `Agent.tools` 仍存工具集名（AgentTool.getName()），`AgentExecutor` 消费 `List<ToolSetInfo>` 的链路**完全不动**；
- 变化仅在展示与选择体验：智能体编辑页的工具选择列表按**插件分组**展示（插件 → 工具集两级树），勾选粒度仍是工具集；
- `ToolSetInfo` 新增 `pluginId`、`pluginName` 字段，`/tools/api/list` 响应同步扩展（旧字段保留，前端向下兼容）。

### 3.4 HTTP API 变更

| 现端点 | 变化 |
|--------|------|
| `GET /tools/api/list` | 响应增加 `pluginId/pluginName`；可另增 `GET /plugins/api/list`（插件级聚合视图） |
| `POST /tools/api/unload`（toolName+toolVersion） | 改为 `POST /plugins/api/unload`（pluginId），保留旧端点转发兼容 |
| `GET /tools/api/export/{toolName}/{toolVersion}` | 改为 `GET /plugins/api/export/{pluginId}`（导出整插件清单） |
| `POST /api/plugins/{toolName}/invoke` | **新增** `POST /api/plugins/by-id/{pluginId}/invoke`（插件级）；旧端点保留 → 路由到 Legacy 适配或"单工具插件" |
| `GET /api/plugins/assets` | 不变（本就是插件级） |
| WebSocket `cmd.toolName` | 新增 `pluginId` 字段，`toolName` 保留（前端 `PluginHook.register` 兼容旧订阅方式） |

### 3.5 LLM 管理工具（ToolManagerTool → PluginManagerTool）

`pluginTool` 工具集升级为按插件粒度描述能力（"安装/卸载/列出插件，插件可含多个工具集"），`@Tool` 方法参数从工具名改为插件名/包路径。

## 4. 插件仓库分层（问题四）

### 4.1 清单格式 v2（以 AgentPlugin 为主体）

现 `PluginExportInfo extends ToolSetInfo`（单工具集）。v2 改为独立插件清单：

```json
{
  "manifestVersion": 2,
  "id": "database",
  "name": "数据库插件",
  "description": "提供数据库查询与结构管理能力",
  "version": "2.0.0",
  "author": "xxx",
  "url": "https://gitee.com/hgflydream/hopaw-agent",
  "icon": "<svg ...>",
  "keyword": "数据库,SQL,查询",
  "jarFileName": "hopaw-tool-database-2.0.0.jar",
  "fileSize": 123456,
  "sha256Hash": "…",
  "provides": {
    "tools": [
      { "name": "databaseQuery", "description": "SQL 查询工具集", "toolCount": 4 },
      { "name": "databaseSchema", "description": "结构管理工具集", "toolCount": 3 }
    ],
    "frontendAssets": 2,
    "invoke": true
  },
  "configItems": [ … ]
}
```

- v1 清单（无 `manifestVersion` 字段）→ 解析时自动包装为 v2（`provides.tools` 取单工具集），**存量仓库数据零迁移**；
- 仓库目录结构 `packages/<pluginId>/<version>/` 不变，升级的只是目录内 JSON 的语义。

### 4.2 仓库与商店的分层展示

- `PluginRepoService.scanPlugins()` 条目从"工具集"改为"插件"：一个插件条目 = 基本信息.setIcon + N 个版本，每版本声明 `provides`；
- `plugin-store.html` 卡片改为插件主体（插件名/图标/描述 + 提供的工具集徽标 + 前端组件徽标），版本列表不变；
- 安装流程不变（下载 zip → 校验 sha256 → 落盘 → 热加载），仅"已安装判断"从 toolName+version 改为 pluginId+version。

### 4.3 仓库服务端（hopaw-plugin-repo）

`PluginRepoController` / 前端管理页的"导入插件包"校验逻辑升级为优先读 v2 清单；`PluginRepoResult` DTO 增加层级结构（插件 → 版本 → provides）。该模块独立部署，升级可与主程序解耦（清单向后兼容保证了新旧版本主程序/仓库可交叉工作）。

## 5. 实施阶段划分

| 阶段 | 模块 | 内容 | 兼容性 |
|------|------|------|--------|
| **S1 契约层** | hopaw-contract | 新增 `AgentPlugin`、`PluginDescriptor`（DTO）、`IAgentPluginService`；`AgentTool` 元数据方法标 @Deprecated（default 委托） | 纯增量，零风险 |
| **S2 加载与注册** | hopaw-infra | `JarPluginLoader` 优先扫 `AgentPlugin` 实现，无则走 Legacy 适配；`DynamicToolRegistry` → `PluginRegistry`（key=pluginId，内部保留 jarFileName→pluginId 映射以兼容查询）；`PluginEntry` 持有 AgentPlugin | Legacy 插件行为不变 |
| **S3 服务拆分** | hopaw-infra | `AgentToolService` 拆为 `PluginManagerService` + `ToolSetService`；配置两级分发；导出/冲突检测/升级判断全部改用插件元数据（消灭 3 处 `get(0)` 假设） | 对外 API 旧端点保留 |
| **S4 应用层** | hopaw-app | tools.html 两级管理树（插件 → 工具集）；智能体编辑页工具选择按插件分组；新增插件级 API；`PluginInvokeController` 增加 by-id 路由；ToolManagerTool 升级 | 旧 URL/字段全保留 |
| **S5 仓库** | hopaw-plugin-repo | 清单 v2 解析 + v1 自动包装；商店页按插件展示 | 旧仓库数据零迁移 |
| **S6 生态迁移** | tools/*、docs | 挑 1-2 个代表性插件（建议 database：演示"1 插件多工具集"；canvas：演示"前端组件+工具"）改造为显式 AgentPlugin；更新《插件开发说明.md》 | 其余插件继续 Legacy |

**建议顺序**：S1 → S2 → S3 是一条主线（后端模型重塑），S4/S5 可并行，S6 收尾。

## 6. 风险与待决策问题

1. **invoke 路由歧义**：旧 `/api/plugins/{toolName}/invoke` 的路径参数既是工具集名又像插件名。v2 后建议"名字空间分离"：插件 id 与工具集名不得相同（加载期校验），避免 by-id 路由误伤。
2. **存量配置键迁移**：Legacy 插件保持 `tool.<name>.` 前缀 vs 统一迁到 `plugin.<id>.`——本规划推荐双轨（决策点，见 §3.2），若选统一迁移需写一次性数据迁移脚本。
3. **插件启停是新增状态**：需要持久化（建议 SQLite 新表 `plugin_state`：pluginId/enabled/installedVersion），这是目前完全没有的概念，涉及 UI 与 ToolSet 组装逻辑的过滤。
4. **JAR 文件名 vs pluginId**：允许一个 pluginId 的不同版本 JAR 共存于 plugins/ 目录吗？建议不允许（同名 id 第二个 JAR 拒绝加载），升级必须走覆盖。
5. **`hopaw-plugin-repo` 独立部署的版本滞后**：主程序升级到 v2 清单后，旧仓库仍只收 v1 包——靠 v1 自动包装兜底，但"多工具集插件"在旧仓库上不可见（只能看到第一个工具集）。
6. **前端资产的作用域**：插件禁用时前端资产不注入，需要 plugin-loader.js 感知插件状态（assets 清单接口按启停过滤即可，实现简单但要记得做）。
7. **全量打包卡在 hopaw-plugin-repo 的既有构建问题**（见《插件开发说明.md》§9）：S5 动仓库模块前建议先修，否则本地验证困难。

## 7. 验收标准

- [ ] 一个 JAR 内实现 1 个 AgentPlugin + 2 个 AgentTool：插件管理页显示 1 个插件、2 个工具集；导出/升级/冲突检测均以插件为单位；
- [ ] 一个**无任何 AgentTool**、仅含 plugin-assets.json 的纯前端 JAR：可安装、资产正常注入、可卸载；
- [ ] 现有 13 个 Legacy 插件零改动通过全部既有功能（加载、@Tool 调用、配置、前端注入、导出/安装）；
- [ ] 智能体编辑页按插件分组选择工具，`Agent.tools` 存储格式与既有数据完全兼容；
- [ ] v1 插件包在 v2 主程序、v2 插件包（v1 清单视图）在旧主程序上均可安装。
