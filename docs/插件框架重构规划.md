# 插件框架重构规划 v2：以 AgentPlugin 为主体的分层插件体系（无兼容负担版）

> 状态：规划稿（未实施）
> **前提定案（2026-09-20）**：不考虑历史兼容。部署时完全重新初始化——`agent.db`（含 SysConfig、Agent 绑定）、`plugins/` 目录、插件仓库数据全部从零开始。
> 本版基于该前提对 v1 规划（含其 §8 复核结论）做全面简化：所有为兼容而设的机制一律删除。
> 关联文档：`docs/插件开发说明.md`（现行体系）
> 涉及模块：`hopaw-contract`、`hopaw-infra`、`hopaw-app`、`hopaw-plugin-repo`、`tools/*`

## 0. 前提变更带来的简化总览

v1 规划及其复核（§8）中的下列机制**全部作废删除**：

| # | v1 中的兼容机制 | 作废理由 | 处置 |
|---|----------------|----------|------|
| C1 | **LegacyAgentPluginAdapter**（无 AgentPlugin 的 JAR 自动包装，13 个存量插件"零改动运行"） | 存量插件将随重新初始化一并迁移 | 删除。加载器**强制要求** JAR 内有显式 `AgentPlugin` 实现，没有即拒绝安装 |
| C2 | **配置前缀硬约束**（`tool.<name>.` 永久不可变 + 插件级另立 `plugin.<id>.*` 双轨） | SysConfig 全部重来，无存量键可丢 | 不再是"硬约束"，仅是设计选择（见 §3.2） |
| C3 | **接口方法只 @Deprecated 不物理删除**（AgentTool 上的元数据/生命周期/invoke 降级保留） | 无存量源码需要继续编译 | AgentTool **彻底瘦身**，多余方法物理删除 |
| C4 | **legacyNames 别名**（pluginId 改名后商店"已安装"误判） | 无存量安装状态 | 删除。pluginId 自由命名 |
| C5 | **仓库清单 v1 自动包装为 v2** | 仓库数据从零开始 | 仓库直接只认 v2 清单 |
| C6 | **assets 路由双 key 回退**（pluginId 未命中回退 jarFileName） | 无已缓存页面/客户端 | 直接切换为 pluginId |
| C7 | **旧 HTTP 端点保留转发**（`/tools/api/unload` 等共存） | 无旧前端/客户端 | 端点直接替换，不保留旧路由 |
| C8 | **IAgentToolService 外观 + 委派过渡**（12 个注入点不敢动签名） | 接口签名可以随便改 | 直接拆分重命名，注入点一次性更新 |

**作废后的净收益**：代码量预估减少约 1/3（适配器、双轨、别名、回退、过渡端点全免），接口设计干净，无"新旧两套口径"并存的过渡态。

**新增代价（唯一的）**：13 个存量插件从"可选迁移"变为**强制全量迁移**——每个插件需补一个 `AgentPlugin` 实现类。为此提供 `AbstractAgentPlugin` 基类，把单工具插件的迁移成本压到约 30 行样板代码（详见 §6 S6）。

## 1. 现状研究结论（不变，仍有效）

### 1.1 现行加载与注册链路

```
plugins/*.jar
  └─ JarPluginLoader（启动扫描 + 热装入口）
      └─ PluginClassLoader.scanAgentToolClasses()   ← 扫描 JAR 内所有 AgentTool 实现类
          └─ 逐个 newInstance() + autowireBean() + asyncInit()
              └─ DynamicToolRegistry.register(jarFileName, classLoader, List<AgentTool>)
                  └─ PluginEntry（key = JAR 文件名，含 tools 列表 + plugin-assets.json 解析结果）
```

消费侧：

- `AgentToolService.getToolSets()`：内置 Bean（`getBeansOfType(AgentTool.class)`）+ 插件工具，逐个 AgentTool 生成一个 `ToolSetInfo`（扫描类上的 `@Tool` 方法）；
- `AgentService.getToolSetFromAgent()`：按 `Agent.tools`（逗号分隔的**工具集名**）过滤 `ToolSetInfo`，交给 `AgentExecutor`；
- 前端 `tools.html` 平铺展示 `ToolSetInfo` 列表（卸载/导出按钮挂在每个工具集上）；
- 插件仓库 `hopaw-plugin-repo`：`packages/<name>/<version>/` 目录 + 导出清单 `PluginExportInfo`（继承自 `ToolSetInfo`）。

### 1.2 问题一结论：每个插件是不是只能注册一个 AgentTool？

**技术上不是，事实上一却是。**

- 加载器本身支持多个：`scanAgentToolClasses()` 返回 List，一个 JAR 里有 N 个 AgentTool 类会全部实例化并注册；
- 但**整个管理层都建立在"1 JAR = 1 AgentTool = 1 ToolSet"的假设上**，多工具 JAR 是"半残支持"：
  - 冲突检测 `detectConflicts()` 用 `entry.getTools().get(0).getName()` 当插件名（`AgentToolService` L370）；
  - 升级判断 `previousVersion = existing.getTools().get(0).getVersion()`（L513/L573/L590，共 3 处 `get(0)` 假设）；
  - 导出只带一个工具集的元数据，同一 JAR 的其余工具集元数据丢失；
  - `tools.html` 平铺展示，多工具 JAR 会出现多个指向同一 JAR 的卸载按钮；
  - 配置只有工具级，插件级公共配置（如"数据库插件"给 3 个工具共用的连接信息）无处安放。
- 现实佐证：`tools/` 下 13 个插件模块**全部**只含一个 AgentTool 类。

### 1.3 其他结构性问题（与兼容无关，重构必须解决）

| # | 问题 | 代码位置 |
|---|------|----------|
| P1 | 插件身份寄生在工具上：name/version/author/url/icon/keyword 定义在 `AgentTool` 接口 | `AgentTool.java` |
| P2 | 注册表 key 是 JAR 文件名而非插件标识：改名 JAR 即视为不同插件 | `DynamicToolRegistry` |
| P3 | "插件"存在两套口径：前端资产是 JAR 级（plugin-assets.json），invoke/WebSocket 指令却是工具集级 | `PluginEntry` / `PluginInvokeController` |
| P4 | 导出/仓库清单以工具集为主体：`PluginExportInfo extends ToolSetInfo` | `PluginExportInfo` / `PluginRepoService` |
| P5 | LLM 管理工具按工具集名操作，与"装的是插件"错位 | `ToolManagerTool` |
| P6 | 卸载时 `cleanConfig` 只清被点中的那一个工具集的配置，多工具插件会残留 | `AgentToolController.unloadPlugin` |
| P7 | 前端联动缺口：智能体表单平铺 checkbox 依赖直接子元素选择器、`plugin-store.js` 用字符串比较判版本（1.10.0 < 1.9.0 误判）、`index.js` 缺 toolSet→plugin 映射 | `agent-form-fragments.html` / `plugin-store.js` / `index.js` |

### 1.4 可直接继承的资产

- `PluginEntry` + `PluginClassLoader`：JAR 级生命周期（classloader 隔离、资源缓存、临时文件清理）完备，无需大改；
- `plugin-assets.json` + `PluginAsset` + `PluginAssetController` + 前端 `plugin-loader.js`/`plugin-hook.js`：前端组件注入体系天然插件级，直接平移；
- `@Tool` 方法扫描（`scanToolSet`）、安全级别、审批链路：工具级机制成熟，保持不动；
- `Agent.tools` 按工具集名绑定的粒度：设计合理，保留（这不是兼容妥协，而是"智能体使用以 ToolSet 为主"的正确抽象）。

## 2. 目标架构：AgentPlugin 主体模型

### 2.1 核心思想

把"插件"从 AgentTool 的一个侧面，提升为**独立的一等公民接口**，并且**由插件充当工具的工厂**：

```
AgentPlugin（插件主体，1 JAR = 1 实例）
 ├── 插件元数据：id / name / version / author / url / description / icon / keyword
 ├── 插件生命周期：asyncInit() / destroy() / onConfigChanged()
 ├── 插件级配置：getConfigItems() + 前缀 "plugin.<id>."
 ├── 能力声明 + 工具工厂：getTools() → 0..N 个 AgentTool（插件自建实例，可注入共享资源）
 ├── 前端组件：plugin-assets.json（沿用，jar 级）
 └── 通用调用：invoke(String toolRef, Map<String, Object> params)
```

`AgentTool` **彻底瘦身为纯工具**（物理删除元数据/生命周期/invoke，无 @Deprecated 过渡）：

```java
public interface AgentTool {
    String getName();            // 工具集名（全局唯一，Agent 绑定、前端 hook 过滤仍用它）
    String getDescription();
    // @Tool 方法 + @ToolSecurityLevel：不变
    default List<ToolConfigItem> getConfigItems() { return List.of(); }   // 工具级可选配置
    // 删除：getVersion/getAuthor/getUrl/getIcon/getKeyword → AgentPlugin
    // 删除：asyncInit/destroy → AgentPlugin（工具需要资源，由插件在创建工具实例时注入）
    // 删除：invoke → AgentPlugin
    // 删除：getConfigPrefix（前缀由框架按约定计算，插件不再自行拼接）
}
```

### 2.2 关键设计决策

**D1 - 一个插件 0..N 个工具**：`getTools()` 返回空列表合法——纯前端组件插件（只注入 js/css/html）、纯 invoke 服务插件都是合法形态。加载器拒绝条件改为：**既无 AgentPlugin 实现也无前端资产**。

**D2 - 插件标识**：`AgentPlugin.getId()` 即 pluginId，全局唯一，作为注册表主键（替代 JAR 文件名）。JAR 文件名仅作物理定位。加载时同 id 已注册 → 拒绝并提示"插件已安装，请走升级"。

**D3 - 工具命名空间**：`@Tool` 工具名保持全局唯一（沿用冲突检测），约定 `<pluginId>_<method>` 前缀（现状已如此：`gomoku_startGame`）。`ToolSetInfo` 增加 `pluginId` / `pluginName` 归属字段（字段可以直接加，无需考虑旧消费方）。

**D4 - 插件即工具工厂（本版新增，取代 v1 的 Legacy 适配）**：

```
加载：newInstance(AgentPlugin) → autowireBean(插件) → 插件.asyncInit()
      （asyncInit 内构建共享资源：连接池、HttpClient 等）
      → 插件.getTools() 取工具实例 → 逐个 autowireBean(工具) → 注册
销毁：插件.destroy()（插件负责释放自己创建并分发给工具的全部资源）→ 关闭 classloader
```

- 多工具插件共享连接池的时序问题在**设计上消失**：资源由插件先建、工具后拿，不存在"工具先于插件 init"的可能；
- 工具不再有生命周期方法，接口和心智模型都更简单；
- 迁移样板收敛到 `AbstractAgentPlugin` 基类（见 §6 S6）。

**D5 - 接口契约**（hopaw-contract 新增）：

```java
public interface AgentPlugin {
    String getId();                          // 插件唯一标识
    String getDescription();
    default String getName()    { return getId(); }
    default String getVersion() { return "1.0.0"; }
    default String getAuthor()  { return "Agent Plugin"; }
    default String getUrl()     { return "https://gitee.com/hgflydream/hopaw-agent"; }
    default String getIcon()    { return "plugin.svg"; }   // jar 内 static/icons/plugins/
    default String getKeyword() { return ""; }
    default void asyncInit()    { }
    default void destroy()      { }
    default List<ToolConfigItem> getConfigItems() { return List.of(); }
    default void onConfigChanged() { }
    List<AgentTool> getTools();              // 0..N，asyncInit 后调用
    default Map<String, Object> invoke(String toolRef, Map<String, Object> params) {
        throw new UnsupportedOperationException("插件未提供 invoke 能力");
    }
}
```

`invoke` 的 `toolRef` 用于多工具插件的路由（传工具集名；为空时由插件自行决定默认行为）。v1 复核中"invoke 委托 tools[0] 导致第二工具不可达"的问题在显式 AgentPlugin 下不存在——路由权在插件自己手里。

## 3. 管理层级拆分

### 3.1 两级模型

```
一级：插件管理（PluginRegistry / PluginManagerService）
 ├── 安装 / 升级 / 卸载（以 pluginId + version 为准）
 ├── 启用 / 禁用（新增运行时状态，禁用 = 工具不进 ToolSets、前端资产不注入）
 ├── 插件级配置（plugin.<id>.* 配置页）
 └── 插件元数据展示（版本/作者/来源/前端资产数/工具数）

二级：插件内工具管理（ToolSetService）
 ├── 工具集（AgentTool）列表 + @Tool 方法明细（参数/描述/安全级别）
 ├── 工具级配置（沿用 tool-config 模板）
 └── 工具集启停（可选：粒度到单个 AgentTool）
```

服务层拆分（现 `AgentToolService` 职责过载，一并拆解；**不再需要外观委派过渡**，直接改）：

| 现类 | 拆分后 | 职责 |
|------|--------|------|
| `AgentToolService` | `PluginManagerService` | 插件安装/升级/卸载/启停/导出、冲突检测（12 个 `IAgentToolService` 注入点一次性更新，顺手消灭 `ToolConfigController` 直接依赖实现类的坏味道） |
| `AgentToolService` | `ToolSetService` | ToolSet 扫描（`scanToolSet` 平移）、按 agent 组装 `List<ToolSetInfo>`、`getToolNameAndDescriptionMap` |
| `DynamicToolRegistry` | `PluginRegistry` | key = pluginId；`PluginEntry` 持有 `AgentPlugin` 实例 + `List<AgentTool>` + assets + jar 物理路径 |

### 3.2 配置两级化（设计选择，非兼容约束）

重新初始化后配置键无存量包袱，但仍采用**两个独立前缀段**，理由是简单清晰而非兼容：

- **插件级**：`plugin.<pluginId>.*`，`AgentPlugin.getConfigItems()` 声明，用于多工具共享的公共配置（连接信息、凭证等）；
- **工具级**：`tool.<工具集名>.*`，`AgentTool.getConfigItems()` 声明——工具集名本就全局唯一，`ToolConfigService` 与 `tool-config` 页面逻辑可原样复用；
- `ConfigChangeEvent` 分发：`plugin.<id>.` 前缀 → 插件 `onConfigChanged()`；`tool.<name>.` 前缀 → 对应工具 `onConfigChanged()`；
- 前缀由**框架统一计算**（从 AgentTool/AgentPlugin 接口移除 `getConfigPrefix()`），插件通过 `IPluginConfigService.get(id, key)` / `IToolConfigService.get(name, key)` 读配置，不再自行拼 key——消灭 8 个插件各自 `getByKey(getConfigPrefix()+...)` 的散装读法；
- 前端配置页：一级页面选插件，二级页内分「插件配置」区块 + 每个工具集的「工具配置」区块。

### 3.3 智能体使用侧：仍以 ToolSet 为主体（设计保留，非兼容妥协）

- `Agent.tools` 仍存工具集名，`AgentExecutor` 消费 `List<ToolSetInfo>` 的链路不动；
- 变化在展示与选择体验：智能体编辑页的工具选择列表按**插件分组**展示（插件 → 工具集两级树），勾选粒度仍是工具集；
- `ToolSetInfo` 新增 `pluginId`、`pluginName` 字段，`/tools/api/list` 响应直接扩展（无需保留旧字段口径的顾虑，但旧字段本身有用，保留）。

### 3.4 HTTP API（直接替换，不保留旧路由）

| 现端点 | 新端点 / 变化 |
|--------|--------------|
| `GET /tools/api/list` | 响应增加 `pluginId/pluginName`；另增 `GET /plugins/api/list`（插件级聚合视图） |
| `POST /tools/api/unload`（toolName+toolVersion） | **替换为** `POST /plugins/api/unload`（pluginId） |
| `GET /tools/api/export/{toolName}/{toolVersion}` | **替换为** `GET /plugins/api/export/{pluginId}`（导出整插件清单） |
| `POST /api/plugins/{toolName}/invoke` | **替换为** `POST /api/plugins/{pluginId}/invoke`，body 含 `toolRef` |
| `GET /api/plugins/assets` | 不变（本就是插件级），`plugin` 字段语义由 JAR 文件名改为 **pluginId** |
| `GET /api/plugins/{plugin}/assets/**` | 路径变量改为 pluginId，直接切换 |
| WebSocket `cmd.toolName` | 指令结构改为 `cmd.pluginId + cmd.toolName`（前端 `PluginHook.register` 同步改） |

### 3.5 卸载与清理语义（修复现状 P6）

卸载以 pluginId 为单位，`cleanConfig` 必须遍历：

1. 插件级配置：`plugin.<id>.*` 全部键（含 MAP 散键）；
2. 插件下**所有**工具集的 `tool.<name>.*` 键（含 MAP 散键）。

导出同理：导出整插件（pluginId），不再接受 toolName/version 维度。

### 3.6 LLM 管理工具（ToolManagerTool → PluginManagerTool）

`pluginTool` 工具集升级为按插件粒度描述能力（"安装/卸载/列出插件，插件可含多个工具集"），`@Tool` 方法参数从工具名改为插件名/包路径。

## 4. 插件仓库分层

### 4.1 清单格式 v2（以 AgentPlugin 为主体，唯一格式）

仓库**只认 v2**，无 v1 包装逻辑：

```json
{
  "manifestVersion": 2,
  "id": "database",
  "name": "数据库插件",
  "description": "提供数据库查询与结构管理能力",
  "version": "2.0.0",
  "author": "xxx",
  "url": "https://gitee.com/hgflydream/hopaw-agent",
  "icon": "<svg ...>",
  "keyword": "数据库,SQL,查询",
  "jarFileName": "hopaw-tool-database-2.0.0.jar",
  "fileSize": 123456,
  "sha256Hash": "…",
  "provides": {
    "tools": [
      { "name": "databaseQuery", "description": "SQL 查询工具集", "toolCount": 4 },
      { "name": "databaseSchema", "description": "结构管理工具集", "toolCount": 3 }
    ],
    "frontendAssets": 2,
    "invoke": true
  },
  "configItems": [ … ]
}
```

仓库目录结构 `packages/<pluginId>/<version>/` 不变（本就是插件级目录，只是条目 name 的语义从"首个工具集名"修正为 pluginId）。

### 4.2 仓库与商店的分层展示

- `PluginRepoService.scanPlugins()` 条目从"工具集"改为"插件"：一个条目 = 基本信息 + N 个版本，每版本声明 `provides`；
- `plugin-store.html` 卡片改为插件主体（插件名/图标/描述 + 工具集徽标 + 前端组件徽标），版本列表不变；
- "已安装判断"从 toolName+version 改为 **pluginId+version**（重新初始化后不存在别名匹配问题）；
- 顺手修复 `plugin-store.js` 的**字符串版本比较 bug**（`1.10.0 > 1.9.0` 误判），改为语义化版本比较。

### 4.3 仓库服务端（hopaw-plugin-repo）

`PluginRepoController` / 管理页的"导入插件包"校验逻辑只读 v2 清单；`PluginRepoResult` DTO 增加层级结构（插件 → 版本 → provides）。

v1 的"S2.5 低风险身份修复""S3' 拆分放最后"等排序技巧都是为兼容过渡设计的，现在**不需要**——可以直接按依赖顺序线性推进：

| 阶段 | 模块 | 内容 |
|------|------|------|
| **S0 决策定案** | — | **✅ 已完成（2026-09-20）**：§7 四问全部定案 |
| **S1 契约层** | hopaw-contract | `AgentPlugin`（含 `AbstractAgentPlugin` 基类）、`PluginDescriptor` DTO、`IAgentPluginService`。**纯增量，不改 AgentTool**（瘦身挪到 S2，保证 S1 单独可编译） |
| **S2 加载与注册** | hopaw-infra | `JarPluginLoader` 扫 `AgentPlugin` 实现并强制要求；**AgentTool 瘦身在此阶段与全部消费方同步修改**（infra/biz/app + 13 插件中先迁 demo）；`DynamicToolRegistry` → `PluginRegistry`（key=pluginId，同 id 第二个 JAR 拒绝加载）；插件即工具工厂的加载/销毁流程；纯前端插件安全校验（sha256 强制 + sandbox 声明）；**用 demo 插件冒烟** |
| **S3 服务与 API** | hopaw-infra + hopaw-app | `AgentToolService` 拆为 `PluginManagerService` + `ToolSetService`（12 个注入点一次更新）；配置两级分发 + `IPluginConfigService`；新端点替换旧端点；卸载/导出/冲突检测改用插件元数据（消灭 3 处 `get(0)`）；`ToolManagerTool` 升级 |
| **S4 前端 UI** | hopaw-app | `tools.html` 两级管理树（插件 → 工具集）；智能体编辑页按插件分组（修 §1.3-P7 三处联动）；`PluginInvokeController`/WebSocket 指令切换 pluginId |
| **S5 仓库** | hopaw-plugin-repo | 清单 v2（唯一格式）；商店页按插件展示；语义化版本比较。**前置**：先修该模块既有构建问题（《插件开发说明.md》§9），否则本地验证困难 |
| **S6 全量插件迁移** | tools/*、docs | 13 个插件全部改造为显式 AgentPlugin（见下方迁移配方）；更新《插件开发说明.md》 |

**S6 迁移配方**（每个插件约 30 行样板）：

1. 新增 `XxxPlugin extends AbstractAgentPlugin`：搬入原 `getName/getVersion/getAuthor/...` 元数据（id 建议沿用原工具集名，纯为省事，非约束）；
2. 原 `asyncInit()` 里建资源/连接池的代码上移到插件的 `asyncInit()`；
3. 插件 `getTools()` 返回原 AgentTool 实例（`new SshTool(连接池)` 或直接 `new SshTool()` + autowire 兜底）；
4. 原 AgentTool 类删掉元数据方法与生命周期方法，只留 `getName/getDescription/@Tool 方法/getConfigItems`；
5. 插件自读配置处改用 `IPluginConfigService`/`IToolConfigService`，删掉 `getConfigPrefix()` 拼接。

迁移顺序建议：demo（S2 冒烟）→ database（演示"1 插件多工具集"）→ canvas（演示"前端组件 + 工具"）→ 其余批量。

## 6. 验收标准

- [ ] 一个 JAR 内实现 1 个 AgentPlugin + 2 个 AgentTool：插件管理页显示 1 个插件、2 个工具集；导出/升级/冲突检测均以插件为单位；
- [ ] 一个**无任何 AgentTool**、仅含 plugin-assets.json 的纯前端 JAR：可安装、资产正常注入、可卸载；
- [ ] 13 个插件全部迁移完成，逐一通过功能清单：加载、@Tool 调用、配置读写、前端注入、导出/安装、invoke（如原支持）；
- [ ] 卸载插件后，`plugin.<id>.*` 与其全部工具集的 `tool.<name>.*` 配置键被清干净（含 MAP 散键）；
- [ ] 智能体编辑页按插件分组选择工具，`Agent.tools` 存储格式不变（工具集名）；
- [ ] 仓库全新初始化后仅 v2 清单可用：上传、列表、安装、升级、已安装/可更新判定均正确（含 1.10.0 vs 1.9.0 版本比较）；
- [ ] 无 AgentPlugin 实现且无前端资产的 JAR 被拒绝安装并给出明确报错。

## 7. 决策定案（2026-09-20 用户确认，按建议方案执行）

v1 的 Q2（getId 沿用旧名 + legacyNames）因无兼容而**消失**——pluginId 自由命名；Q3（插件级配置要不要做）因无兼容顾虑，已直接定为**做**（`plugin.<id>.*` 段 + 二级配置页）。剩余 4 问已全部定案：

| # | 问题 | **定案** | 落地阶段 |
|---|------|----------|----------|
| Q1 | 内置工具（hopaw-biz 的 @Component）在两级管理里如何归属？ | **管理页顶层分「插件 / 内置工具」两个 Tab**，内置工具保持平铺展示 | S4 |
| Q2 | 是否引入"插件启用/禁用"状态？禁用后悬空绑定如何处理？ | **做**：`plugin_state` 表（pluginId/enabled/installedVersion）+ ToolSet 组装过滤 + 智能体编辑页提示"工具不可用（插件已禁用）"+ 前端资产显式 unload 或提示刷新 | S3（表与过滤）/ S4（UI 提示） |
| Q3 | 是否正式支持"零 AgentTool 的纯前端插件"？JS 注入权限如何处理？ | **支持**，配套安全策略：① 安装链路强制 sha256 校验（已有，保留）；② 第三方 `pluginSourceUrls` 来源需用户显式确认才允许纯前端插件；③ 纯前端插件的 js 仅注入到指定容器（plugin-assets.json 增加 `sandbox` 声明，默认不放开全局 index 注入） | S2（加载校验）/ S5（仓库侧） |
| Q4 | 允许同一 pluginId 的多个版本 JAR 共存吗？ | **不允许**：同 id 第二个 JAR 拒绝加载并报错，升级走覆盖安装（uninstall → write → load） | S2 |

## 8. 风险清单（无兼容版）

1. **迁移期功能回归**：13 个插件强制迁移是本版新增的最大工作量，靠 §6 的逐插件功能清单兜底；建议每迁移一个就跑一遍冒烟，不要攒到最后。
2. **一次性切换无灰度**：旧端点、旧清单、旧指令格式全部直接替换，切换点即 S3/S4/S5 完成时——前后端必须同版本发布，不能交叉部署（对重新初始化的使用方式而言可接受，但需知晓）。
3. **`hopaw-plugin-repo` 既有构建问题**（《插件开发说明.md》§9）：S5 前必须先修，否则无法本地验证。
4. **纯前端插件的安全面**：见 §7 Q3，属安全问题而非兼容问题，不因重新初始化而消失。
5. **插件启停与悬空绑定**：见 §7 Q2，运行时设计问题，同样与兼容无关。
